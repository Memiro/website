# Переписывание Memiro по agent-coding-instruction: реестр решений

Документ для гриллинга. Каждое решение — одной строкой, без обоснований (они в истории обсуждения 2026-08-25). Гриллинг завершён 2026-08-25: решения 1–60, нерешённого не осталось (один needs-info на деплой).

Контекст: сайт не запущен, текущий код — MVP и переписывается с нуля. Из старого репозитория переезжают только доменные документы: `CONTEXT.md` и ADR-0002…0010. Канон стека и процесса — `agent-coding-instruction.md` (FastAPI + SQLAlchemy 2.0 async + dishka); референсный репозиторий — `lubaskinc0de/dreamteams`. Требование владельца: Django-админка сохраняется; расчёт цены — главная ценность сайта и должен быть образцово чистым, строго по DDD и чистой архитектуре, плотно покрыт тестами.

## Решено

### Стек и топология

1. Вариант A: стек инструкции дословно — FastAPI, async SQLAlchemy 2.0 (imperative mapping), alembic, dishka, structlog + OTel. Формат репозитория — в точности §2 инструкции.
2. Пишем с нуля; старый код не мигрируется. Старый репозиторий — справочник по домену.
3. Один bounded context `memiro`; второго пакета-контекста не заводим. `memiro_common/` — примитивы §5 дословно (Clock, UoW, AppError, @interactor, logger) + `observability/`.
4. Сервисы за nginx: `frontend` (Astro SSR, Node), `api` (FastAPI, uvicorn, async), `admin` (Django, gunicorn, WSGI, sync), `migrations` (one-shot: alembic, затем django migrate). `api` и `admin` — один Python-образ, разные `command:`.
5. Витрина — Astro в SSR-режиме (не SSG), интерактив — островами на Vue (`client:visible`). Калькулятор и форма заявки — острова.
6. Админка вызывает интеракторы напрямую импортом (`async_to_sync`), не по HTTP.
7. Статика админки: `collectstatic` на сборке образа, nginx отдаёт `/static/admin/` с тома.

### Схема и данные

8. Alembic — единственный владелец доменных таблиц. Django-миграции владеют только служебными (`auth_*`, `django_*`). В `env.py` alembic — `include_object`-фильтр, отбрасывающий чужие таблицы.
9. Доменные Django-модели — зеркала: `managed = False`, явный `db_table`, совпадающий с alembic-таблицами.
10. Дрейф зеркал ловит тест `test_admin_mirror_matches_schema.py`: сверка `mapper_registry.metadata` против `django.apps.get_models()` — таблицы, колонки, nullable, грубый тип.
11. Идентификаторы — UUID через PEP 695 `type ProductId = UUID`; в публичных URL — slug.

### Админка

12. Чтение — напрямую по зеркалам: changelist, `list_filter`, поиск, `select_related`, история.
13. Запись — через интеракторы для всего, у чего есть инварианты: `Product`, `Attribute`, `PricingSettings`, `Inquiry`, `Landing`. Шаблон: `save_model`/`save_formset`/`delete_model` → REQUEST-scope контейнера → интерактор; `AppError` → `ValidationError` формы.
14. Прямой CRUD (мимо домена) — только контент без правил: `Work`, `Review`, `FaqEntry`, `Promo`, `SiteContacts`, `LegacyUrl`.
15. Граница пунктов 13/14 — «есть инварианты vs нет», а не «агрегат vs справочник». Единица расхода (`Unit`) — enum домена, в админке не редактируется.
16. Доменные глаголы — `@admin.action` («пересчитать», «опубликовать», «снять»), не CRUD.
17. Оператор админки — не доменная сущность. Права — Django permissions. Большинство интеракторов анонимны, `IdProvider` не инжектят.
18. Фото — порт `ProductImageStorage` (`Local*`/`S3*`); в зеркале — строковое поле-ключ. Заливка из админки — через интерактор в порт.
19. `SingletonModel` исчезает: `PricingSettings`, `SiteContacts` — сущности с известным id; в админке редирект с changelist на единственный объект.
20. `LogEntry`/History работают штатно.

### Домен: агрегаты

21. Критерий границы: правило, обязанное выполняться всегда, держит обоих участников в одном агрегате; правило, терпящее рассинхрон, — в разных, связь событием.
22. Корни: `Product` (внутри `DeclaredValue`, `Variant`), `Attribute` (внутри `AttributeValue`), `PricingSettings` (внутри ступени `SizeSurcharge`), `Inquiry` (внутри `InquiryItem`), `Category`, `Landing` (внутри `LandingCondition`), контентные корни поштучно.
23. «Цена от» товара — производное поле, пересчитываемое командой `replace_variants` последней строкой; снаружи не присваивается. Дубликаты вариантов по размеру+значениям запрещены внутри агрегата.
24. Между агрегатами — ссылки только по id, никогда объектом.
25. Одна транзакция — один агрегат. Кросс-агрегатное — доменное событие, опубликованное строго после коммита (§7.3); событие несёт только идентификаторы.
26. Сигналы Django исчезают. Пересчёт цен — use case `reprice_products`, хендлер событий `TariffChanged`/`PricingSettingsChanged`/…, своя транзакция, пачками.
27. Позиция заявки хранит слепок конфигурации и цены на момент отправки, не пересчитывает по текущим тарифам.

### Расчёт цены (ядро)

28. Один доменный сервис `pricing_service.price_product(product, dictionary, settings, dimensions, chosen) -> Quotation`; всё параметрами, в базу не ходит (§6.3c).
29. Второй реализации расчёта в репозитории нет. Книга xlsx — интерактор `export_workbook` над тем же сервисом; openpyxl-рендер — адаптер `adapters/workbook/`. Запуск — команда собственного CLI (`memiro workbook build`), не management command.
30. `PriceEngine`-Protocol убирается: замена формулы — изменение домена, а не подстановка адаптера.
31. Результат — VO `Quotation` (total, breakdown, verdict); `verdict` — enum `PRICED | BEYOND_LIMITS | NOT_PRICEABLE | HIDDEN` вместо россыпи булевых свойств. Невалидные комбинации состояний непредставимы.
32. Наценка за размер (ADR-0010) реализуется сразу, внутри расчёта, перемножается с коэффициентом формы, множит только помеченные значения.
33. Русские тексты из домена уходят; наружу — машинный `code`, формулировки — дело фронта/админки.
34. Величины — VO: `Millimeters`, `Dimensions`, `Money`, `Rate`, `Area`, `Perimeter`. Правила «поворот изделия», «нулевой предел = нет предела» — внутри VO/сервиса.
35. «Товар дорос до расчёта» — одно межагрегатное правило в `pricing_service` (вместо пяти нынешних предикатов: `is_calculable`, `shows_calculated_price`, `_calculable_product`, `is_charged`, `has_price`).
36. Тонкие правила CONTEXT.md переносятся: `quantity` — дробный `Decimal`; «отсутствие признака» — значение справочника (`marks_absence`), не пустота; пустота = «владелец не дошёл», расчёт молчит.

### Фронт и SEO

37. Sitemap, robots, meta/OG, canonical, JSON-LD, редиректы легаси-URL — на фронте; бэк отдаёт данные (`GET /api/sitemap-entries`, список редиректов и т.п.).
38. Авторизации на фронте нет; глобального стора (Pinia) не заводим — состояние калькулятора живёт в его компоненте.
39. У `frontend/` свой `AGENTS.md`; правила инструкции на TypeScript не распространяются.

### Слои и контракты

40. Админка — вторая презентация того же контекста: `presentation/django_admin/` рядом с `presentation/fast_api/`. Не отдельный пакет уровня `src/` (в отличие от `dreamteams_exporter`, который отдельный контекст): ей нужен импорт `application`, а контекстам импортировать друг друга запрещено.
41. `.importlinter`: `presentation.django_admin` не импортируется никем; не импортирует `adapters.db`; `django` не встречается нигде, кроме `presentation.django_admin` и `bootstrap.django_admin`; `entities`/`application` не знают fastapi/sqlalchemy/dishka/django.
42. Ошибки: §5.3/§12 дословно — плоская иерархия от `AppError`, `code` SCREAMING_SNAKE, таблица `dict[type[AppError], int]` в двух глобальных хендлерах; формат ответа `{code, message, meta}` единственный (HTML-ошибки — забота фронта).

### Процесс

43. Строго §17 (bootstrap) → §18 (по use case): doc-first страница → красный интеграционный тест → домен → приложение → адаптеры → DI → презентация — одним вертикальным PR ≤500–700 строк.
44. Первый срез после скелета — `calculate_price` (walking skeleton + самая плотная часть домена). Далее: `submit_inquiry` → `browse_catalog` → админка (зеркала + тест дрейфа, потом ModelAdmin'ы) → контент/SEO.
45. `AGENTS.md` и ADR новых решений пишутся до первого кода. `CONTEXT.md` разбирается на `docs/entities/` + `docs/value-objects/` по шаблонам §16.2; сам остаётся коротким входом. ADR-0002…0010 переезжают как есть; ADR-0001 (Django-монолит SSR) помечается заменённым.
46. Тесты — §14 целиком: десять правил, testcontainers + template database, типизированный `ApiClient`, фабрики polyfactory, Hypothesis в unit по стратегиям. Максимальная плотность — на `entities/pricing/` и `integration/calculate_price/`.

### Гриллинг 2026-08-25 (раунд 1)

47. Мост админки (бывш. a): порядок фиксирован — сначала интерактор (коммит домена), затем Django-часть (`LogEntry` истории админки, messages-баннеры) best-effort: её падение — warning, домен не откатывается. Решение 20 сужено до «штатно, но best-effort». Кандидат в ADR.
48. Astro подтверждён (бывш. b). SEO переживает будущую смену стека при сохранении URL/301 (`LegacyUrl` уже доменный); триггер пересмотра — появление личного кабинета (тогда — отдельное SPA под своим путём). Фиксируется ADR.
49. Контент без правил (бывш. c) не получает доменных сущностей: read-путь — DTO + read-гейтвей + read-интеракторы; сущность заводится при первом инварианте. Уточняет решение 22.
50. Потолок каталога (бывш. d) зафиксирован владельцем: 100–300 товаров, 3–10 предпосчитанных вариантов на товар. Пересчёт пачками (решение 26) без оптимизаций; граница применимости — в ADR о пересчёте.
51. Кэша нет (бывш. g) и Redis нет в контуре вовсе; `db-up` поднимает только `db`. Триггер пересмотра — метрики после запуска; первым шагом тогда nginx `proxy_cache`, Redis — последним.
52. Тестовая машинерия §14.5 — целиком (бывш. h): канон обязателен. Локальный контур — Postgres в docker (`just up`), SQLite уходит.
53. Канал заявки (бывш. i): приоритет — почта (SMTP-адаптер `InquiryNotifier`), позже возможно мессенджер MAX. БД — всегда, нотификация best-effort (как в MVP с Telegram). Детали адаптера — раунд 2.
54. Фото (бывш. i) — локальный диск на docker-томе (`LocalProductImageStorage`), nginx отдаёт `/media/`; S3 — позже заменой адаптера в DI.
55. i18n не нужен (бывш. i): русский захардкожен во фронте.
56. Приватность цен при SSR (бывш. j): единственный публичный расчётный эндпоинт `POST /api/calculate`; наружу — усечённая проекция `Quotation` (итог, дельты выбранных добавок «подсветка +11 500 ₽», verdict-код), полный breakdown по статьям — только внутрь (админка, книга xlsx). Гейт `hides_calculated_price` действует и на эндпоинт, и на карточку (перенос ADR-0007/0008). Тест-забор: в публичном JSON нет ставок, коэффициентов и статей полотна/кромки.

### Гриллинг 2026-08-25 (раунд 2)

57. Нотификация (бывш. i-остаток): `SmtpInquiryNotifier` напрямую по SMTP (хост/порт/ящик в конфиге) + перенос Telegram-адаптера из MVP вторым каналом; составной нотификатор, каждый канал best-effort, выключается конфигом. MAX — когда понадобится, порт готов. Конкретный ящик/SMTP-провайдер — needs-info у владельца при деплое.
58. Тест дрейфа зеркал (бывш. f): сверяет таблицы, колонки, nullable, грубый тип + уникальные констрейнты. Дефолты не сверяются (источник — только alembic). Во всех зеркалах `on_delete=models.DO_NOTHING` — правила удаления принадлежат БД и домену; конвенция — строкой в AGENTS.md.
59. Мост async (бывш. k): постоянный фоновый поток с одним живым event loop на процесс админки; `bridge.py` отправляет корутины через `run_coroutine_threadsafe`; dishka-контейнер и engine создаются в этом loop'е один раз (честный APP-scope, поведение идентично API-процессу). Кандидат в ADR.
60. Inline-формсеты (бывш. e): `save_model` не пишет, `save_related` собирает корень и детей в один `Update*Data` и вызывает один корневой интерактор — одна доменная транзакция, полная замена детей командой сущности. Схема едина для `Product`+варианты, `Attribute`+значения, `PricingSettings`+ступени, `Landing`+условия. Правка решения 13: `AppError` → `ValidationError` формы невозможен на этапе save; ошибки формата ловит форма (красные поля), бизнес-отказ интерактора → `messages.error` + возврат на форму, ничего не сохранено; точечные дублирующие проверки в `clean()` — по мере надобности.

61. `AGENTS.md` и ADR новых решений (мост админки: порядок записи + loop-поток; Astro с триггером пересмотра; граница пересчёта каталога) пишутся не ад-хок, а в рамках одной из задач плана переписывания — уточнение решения 45: остаются до первого кода, но оформляются как своя задача в очереди.

### Сверка с закрывшимися тикетами MVP 2026-08-26 (owner-revision 18–19)

62. Конструктор вариантов (тикет 18, ADR-0011) переезжает: инлайн-таблицы вариантов в новой админке нет; варианты правятся поштучно командами агрегата `Product` (добавить, поправить, удалить, размножить с другим размером), каждая команда пересчитывает «цену от»; живую цену собранного до сохранения показывает та же точка, что запишет её варианту. Правка решения 23 (не полная замена набора, а поштучные команды; запрет дубликатов по размеру+значениям остаётся) и решения 60 (схема inline-формсетов остаётся для `Attribute`+значения, `PricingSettings`+ступени, `Landing`+условия; `Product`+варианты из неё выходит). Порядок вариантов — поле владельца: на первом подходящем открывается калькулятор покупателя.
63. У расчёта два спрашивающих (ADR-0011): покупательский вопрос проходит все гейты (публикация, считаемый набор, меняемость атрибута, предел производства, погашенная цена) и получает вердикт; владельческий вопрос конструктора гейтов не проходит — вариант заводит тот, кто знает, что производство возьмёт. Сервис, тарифы и число — общие; гейты — принадлежность покупательского вопроса, не ядра. Уточняет решения 28/31/35.
64. Telegram-канала нет: тикет 19 удалил его из MVP по слову владельца «только почта». Нотификатор — SMTP единственным каналом; составной нотификатор и порт остаются точкой расширения (MAX — решение 53 в силе). Правка решения 57. Уроки MVP-адаптера переносятся: таймаут SMTP, шифрование выводится из порта, пустой адрес менеджера — предупреждение в лог, заявка не страдает. Needs-info сузился: провайдер — Яндекс.Почта, ящик отправителя известен; от владельца — адрес менеджера и пароль приложения.

### Решение владельца 2026-08-26 (ветвление)

65. Модель ветвления: рабочий ствол — `dev` (ветка по умолчанию на GitHub, создана из main со всем кодом MVP и документами). Поток: feature-ветка от `dev` → PR → merge в `dev`; `dev` льётся в `main` релизами. В `main` — только продакшн-код. Правка §0-процесса из тикета 02: «в main напрямую не пишем» остаётся, но PR агентов идут в `dev`; очистка от кода MVP (тикет 04, операция владельца) теперь выполняется на `dev`, старый код остаётся в истории git и в `main` до первого релиза. ### Решения владельца 2026-08-27 (состав справочника, тикет 01)

66. Состав справочника нового домена закрыт тремя ответами владельца (owner-revision 21–23, тикет 01 очереди переписывания):
    - **Вид атрибута «да/нет» удаляется.** Виды атрибута — `SELECT` и `NUMBER`. Отсутствие признака остаётся значением справочника с `marks_absence` («без рамы», «без подсветки»); булев вид был второй правдой о том же. Правка ADR-0002, где вид ещё перечислен, — абзацем в самом ADR.
    - **Температура свечения из домена уходит**, остаётся «подсветка» (owner-revision 21 закрывается). Пример зависящего атрибута в документах — «кнопка существует, только когда есть подсветка».
    - **Акции в переписывание не входят.** Ни сущности, ни страницы: блок снят с витрины (ADR-0004), и размер скидки в процентах (owner-revision 23) вернётся отдельным решением владельца вместе с самим блоком.
