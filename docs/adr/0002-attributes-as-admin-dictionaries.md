# Атрибуты товара — справочники в админке, не поля в коде

Ассортимент типов товаров растёт (зеркала, затем душевые перегородки, дальше неизвестно). Характеристики товара сделаны справочником «атрибутов» с привязкой к категории (EAV-лайт, простые типы: выбор из списка, да/нет, число); фильтры каталога строятся из них автоматически. Владелец заводит новую категорию без разработчика.

Отвергнутая альтернатива — жёсткие поля модели на категорию: проще и быстрее в запросах, но каждая новая категория превращается в задачу разработчику и миграцию. Общие для всех товаров поля (название, цена, фото, описание) остаются обычными колонками — в EAV уходят только фильтруемые характеристики.

Справочник с тех пор расширен: значение атрибута несёт единицу расхода и тариф, атрибут — родителя и признак «меняет покупатель», и из тех же атрибутов считается цена (ADR-0007). Обещание этого решения расширение сохраняет: новая настройка — по-прежнему строка справочника, а не миграция.

Строка «атрибут — родителя» выше читается во множественном числе: родителей у атрибута несколько, и связывает их «или» (ADR-0007, уточнение тикета 15).

Список простых типов с тех пор сузился: решением владельца (решение 66 реестра переписывания) вид «да/нет» из домена уходит, остаются выбор из списка и число. Обещание решения это не трогает — уходит вторая правда об отсутствии: «нет рамы» называется значением справочника с признаком `marks_absence`, и булев вид описывал бы то же самое вторым способом.

«Фильтры строятся из них автоматически» с тикета 22 читается с оговоркой: из тех атрибутов, у которых стоит признак «строит фильтр». Автоматизм не пропал — пропало допущение, что всякая характеристика годится в сужение выдачи. Тип полотна описывает не модель, а заказ: любое зеркало делают из любого полотна, и фильтр по нему прятал бы подходящие товары.
