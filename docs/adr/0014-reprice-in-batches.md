# Пересчёт цен каталога — пачками без оптимизаций, потолок зафиксирован

Правка тарифа или параметров расчёта должна пересчитать цены предпосчитанных
вариантов и «цену от» товаров — иначе витрина показывает вчерашние числа. В
MVP это ехало на сигналах Django; сигналы исчезают вместе с MVP.

**Механизм — доменное событие после коммита.** Одна транзакция — один
агрегат: правка `Attribute` или `PricingSettings` коммитится сама по себе, а
затем публикуется событие (`TariffChanged`, `PricingSettingsChanged`, …),
несущее только идентификаторы. Хендлер — use case `reprice_products`: своя
транзакция, товары пересчитываются пачками, каждый — командами собственного
агрегата, «цена от» пересчитывается той же командой последней строкой.
Никаких оптимизаций: ни инкрементального пересчёта только затронутых
вариантов, ни очередей, ни дедупликации событий.

**Граница применимости зафиксирована владельцем: 100–300 товаров по 3–10
предпосчитанных вариантов.** На этом объёме полный пересчёт — секунды, и
любая оптимизация стоила бы дороже, чем экономила. Это осознанный потолок, а
не оценка: рост каталога за границу — повод пересмотреть этот ADR, а не
чинить внезапно медленный пересчёт по месту.

Рассинхрон между правкой тарифа и завершением пересчёта — допустимое окно:
правило, терпящее рассинхрон, и держит агрегаты порознь. Слепки позиций
заявок пересчёт не трогает никогда — позиция хранит конфигурацию и цену на
момент отправки (ADR-0009).

Отвергнуто: пересчёт в той же транзакции, что и правка тарифа (транзакция в
два агрегата, при росте каталога — долгий коммит на пути формы владельца);
пересчёт по расписанию (окно устаревших цен на витрине без причины — событие
уже знает момент правки).
