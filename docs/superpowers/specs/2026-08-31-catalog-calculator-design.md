# Каталог, карточка и калькулятор

## Визуальный эталон

Внешний вид должен воспроизвести прежнюю Django-витрину, а не получить новую
интерпретацию. Эталон хранится в истории на `main`:

- `src/memiro/static/css/site.css` — токены палитры, типографика Golos Text,
  сетка, адаптивность и состояния контролов;
- `src/memiro/templates/base.html` — шапка, навигация и футер;
- `src/memiro/templates/catalog/category.html` и `_card.html` — заголовок
  категории и плитка товара;
- `src/memiro/templates/catalog/product.html` — композиция карточки,
  галерея, блок вариантов и калькулятор.

Фронтенд перенесёт эту композицию и CSS-систему в Astro/Vue: холодную
нейтральную палитру, самохостинговый Golos Text, контейнер 1320 px, тонкие
границы, нулевые скругления и отсутствие теней. Нынешние временные стили
скелета (`Arial`, тёплый фон и узкий контейнер) заменяются. Старый JavaScript
не переносится: его поведение калькулятора заменяет Vue-остров, а его внешний
контракт и вид остаются прежними.

## Цель

Тикет 14 добавляет витрине индексируемые SSR-страницы каталога и карточки
товара, а покупателю — локальный Vue-калькулятор. Витрина получает данные
только из публичного API; расчёт всегда выполняет `POST /api/calculate`.
Ни тарифы, ни коэффициенты, ни строки внутреннего расчёта во фронтенд не
попадают.

## Маршруты и SSR

- `/catalog/` запрашивает `GET /api/catalog/categories` на сервере Astro и
  выводит опубликованные категории.
- `/catalog/[categorySlug]/` запрашивает
  `GET /api/catalog/categories/{categorySlug}/products` на сервере Astro и
  выводит плитку опубликованных товаров. Плитка целиком ведёт в карточку; у
  неё нет действия добавления в заявку.
- `/catalog/[categorySlug]/[productSlug]/` запрашивает
  `GET /api/catalog/products/{productSlug}/` на сервере Astro. Slug категории
  остаётся в адресе как контекст навигации; публичный API разрешает товар по
  slug товара. Страница выводит фото, название, описание, предпосчитанные
  варианты в порядке API и начальную цену `price_from`, когда она есть.

SSR-клиент использует внутренний URL `http://api:8000` из конфигурации
frontend-контейнера; браузерный остров обращается к относительному `/api`,
который nginx проксирует в тот же API. Неуспешный ответ SSR-запроса
преобразуется в страницу 404 для 404 и в нейтральную ошибку сервера для
остальных статусов. SSR не делает расчётов.

## Калькулятор

На карточке Astro передаёт в `Calculator` только публичную проекцию товара;
остров подключается с `client:visible` и хранит всё изменяемое состояние
внутри себя. Первый вариант API становится начальной конфигурацией: его
размер и overrides заменяют объявленные значения товара.

Покупатель меняет размер и значения атрибутов. После изменения калькулятор
собирает форму `{ product_id, width_mm, height_mm, selections }` и отправляет
её на `/api/calculate`. Ответ является единственным источником цены:

- `PRICED`: показать итог и только подписанные дельты выбранных значений;
- `BEYOND_LIMITS`: скрыть денежные поля и предложить оставить пожелание;
- `HIDDEN`: не показывать денежные поля, сообщить, что стоимость уточнит
  менеджер;
- `NOT_PRICEABLE`: сообщить, что конфигурацию ещё нельзя посчитать.

Погашенная цена не отключает сам калькулятор. Подписи дельт получаются из
публичных имён атрибутов и значений в данных карточки; API передаёт только
идентификаторы и сумму дельты. Размерная ступень допускается как нейтральная
фраза о размере, без раскрытия коэффициента.

## Границы и компоненты

- `src/lib/catalog-api.ts` — серверный типизированный HTTP-клиент и DTO
  публичного API.
- `src/pages/catalog/…` — SSR-маршруты, без клиентского состояния.
- `src/components/…` — плитка товара и статическое отображение карточки.
- `src/islands/Calculator.vue` — единственный интерактивный компонент,
  локальный state и вызов расчёта.
- `src/styles/global.css` — перенос токенов, сетки, типографики и адаптивных
  правил legacy `site.css`; шрифт Golos Text подключается локально из
  фронтенд-ассетов.

Новых зависимостей, глобального стора, авторизации и изменения Python API
срез не требует.

## Проверки

Сначала добавляются падающие проверки фронтенда для SSR-запросов, начальной
конфигурации варианта и отображения каждого требуемого вердикта. Затем
реализуется минимум кода, который их делает зелёными. В конце выполняются
`npm run check`, `npm run build`, а также `just lint`, `just static` и
`just test`, поскольку срез зависит от живого API и контура.

Визуальная проверка сравнивает страницы с legacy-шаблонами по структуре и
токенам: шапка/футер, плитка товара, карточка, блок вариантов, калькулятор и
мобильные брейкпоинты. Расхождения допустимы только там, где новый API или
новые правила тикета изменяют данные либо поведение.

## Вне среза

Заявка и её локальное хранение реализуются в тикете 15. Фото из хранилища и
контентные страницы не добавляются: они принадлежат тикетам 20 и 24.
